# 실행 권한, 검증 증거, 병합 보호

## 경계

가드는 일반적인 실수를 줄이는 보조 장치입니다. 임의 셸 프로그램·프로젝트 스크립트를
정적 문자열 검사만으로 격리할 수 없습니다. 실제 권한과 filesystem/network 접근은
네이티브 sandbox/permissions로 제한하세요. 명령 자동 허용 목록은 git 조회로 좁혔고,
git add/commit 및 임의 npm run을 포괄적으로 승인하지 않습니다.

Write/Edit는 실제 경로를 해석해 프로젝트 내부인지 확인합니다. 이름 접두사가 같은
형제 폴더, `..`, symlink/junction 경유 외부 쓰기를 거부합니다. 환경 변수·동적 셸
확장은 검토한 프로젝트 스크립트로 옮깁니다. 민감 파일을 인자로 주는 Bash와 명시적
Read/Grep/Glob 경로도 검사합니다. 디렉터리 전체 검색은 내부에서 파일을 열 수 있으므로
네이티브 민감 파일 deny 규칙과 sandbox가 필요합니다. `.env.example` 등 샘플만 내용에
비밀이 없음을 확인한 후 허용하세요. Claude의 보수적인 Read deny는 샘플도 막을 수 있습니다.

가드는 차단한 전체 명령을 에러에 복사하지 않아 인자에 섞인 비밀의 재노출을 줄입니다.
잘못된 JSON·설정·Git 실패는 자동 승인하지 않습니다. 알 수 없는 도구나 우회 가능한
스크립트 실행은 호스트 권한 정책이 담당하며, 가드를 완전한 DLP로 사용하지 마세요.

## 증거의 의미

검증 실행은 설정된 argv를 shell 없이 실제 실행합니다. 검사 전후 파일 해시가 같고
종료코드가 0일 때만 PASS입니다. 실행 중 코드 생성으로 소스가 바뀌면 다시 검사합니다.
설정된 명령이 올바른 테스트를 실제 실행하는지도 리뷰해야 합니다. 잘못된 테스트 명령의
exit 0만으로 올바른 테스트 커버리지를 인증할 수는 없습니다.

증거는 같은 사용자 권한의 로컬 JSON입니다. 임의 코드를 실행하는 에이전트에 대한
변조 방지 인증서가 아니며, `.harness/local`을 수동 편집하지 않습니다. 검증 로그에
애플리케이션 출력이 담기므로 비밀을 출력하는 테스트는 수정하세요. 이 디렉터리는
Git에서 제외하고, 신뢰되지 않은 PR의 증거·모델 inventory를 그대로 신뢰하지 않습니다.
민감한 저장소는 별도 신뢰 실행 환경의 CI와 독립 리뷰를 필수로 하세요.

## GitHub에서 강제

workflow의 `harness-ci`는 모든 OS/Python 매트릭스가 성공해야 통과합니다. 토큰은
contents:read이고 checkout 인증은 남기지 않습니다. 외부 액션은 커밋 SHA로 고정합니다.
PR 이벤트로 테스트하고 `pull_request_target`에서 신뢰되지 않은 코드를 실행하지 않습니다.

저장소의 Rulesets 또는 Branch protection에서 main에 다음을 적용하세요.

1. PR을 통해서만 병합, force push/branch deletion 금지.
2. `harness-ci`를 필수 검사로 지정하고 최신 base 기준 검사를 요구.
3. 열린 리뷰 대화 해결을 요구. 팀 프로젝트는 추가로 독립 승인자 수를 지정.

기본 규칙 JSON은 `.harness/github-ruleset.json`입니다. 단독 유지관리자가 자신에게
승인을 줄 수 없어 막히지 않도록 승인자 수 기본값은 0이고 필수 CI는 유지합니다.
프로젝트 관리 권한이 있는 계정에서 다음처럼 적용할 수 있습니다. OWNER/REPO는
실제 저장소로 바꾸고 기존 ruleset이 있으면 새로 중복 생성하지 말고 수정하세요.

```sh
gh api --method POST repos/OWNER/REPO/rulesets --input .harness/github-ruleset.json
```

파일을 커밋하는 것만으로 GitHub 보호 설정이 활성화되지는 않습니다. 읽기/코드 쓰기
권한만 있는 연결은 administration 설정을 바꿀 수 없으므로 실제 활성화 상태를 따로
확인해야 합니다. 정책 파일과 적용 상태를 혼동하지 마세요.

## clone 없는 유지보수

GitHub Git Data/Contents API로 원격 브랜치에 변경을 커밋하고 PR을 생성할 수 있습니다.
CI가 실행하는 checkout은 사용자 컴퓨터의 clone과 별개입니다. 정확한 PR head의 모든
필수 검사가 통과했는지 확인하고, 사용자에게 병합 권한을 받은 경우 expected head SHA를
지정해 병합하세요. 새 커밋이 생기면 이전 성공 기록을 재사용하지 않습니다.
