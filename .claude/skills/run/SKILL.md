# /run — 자율 실행 루프

오케스트레이터(메인 세션)가 따르는 절차. 각 단계에서 직접 구현하지 말고 위임한다.

## 0. 상태 확인
- `docs/STATUS.md` 가 있고 진행 중 작업이 있으면 그 지점부터 이어간다.
- 없으면 새 프로젝트로 시작한다.

## 1. 계획 (Plan)
1. 사용자 요청을 읽고 불명확한 점이 **완료를 막을 정도**면 질문한다. 사소한 건 합리적으로 가정하고 PLAN.md 에 "가정" 섹션에 적는다.
2. `/plan` 스킬 절차대로 `docs/PLAN.md` 를 작성한다.
3. reviewer 에게 계획 검토를 위임한다:
   > "docs/PLAN.md 를 검토하라. 누락된 요구사항, 잘못된 태스크 분해, 위험 요소를 찾아라."
4. VERDICT 가 FIX/REJECT 면 계획을 고치고 재검토. 최대 2회.
5. `docs/STATUS.md` 를 "PLANNED" 로 갱신.

## 2. 실행 (Execute)
PLAN.md 의 태스크를 순서대로(의존성 없는 것은 병렬로) builder 에게 위임한다.

위임 프롬프트 형식:
```
태스크 #N: <제목>
목표: <한 줄>
대상 파일: <경로들>
완료 조건: <구체적으로>
참고: docs/PLAN.md 섹션 <X>
```

- 병렬 가능한 태스크는 여러 builder 를 동시에 띄운다. 단, 같은 파일을 건드리는 태스크는 직렬로.
- RESULT 가 BLOCKED 면 원인을 보고 계획을 수정하거나 사용자에게 묻는다.
- 완료된 태스크는 PLAN.md 체크박스를 체크하고 STATUS.md 에 기록.

## 3. 테스트 (Test)
태스크 묶음(또는 마일스톤)이 끝날 때마다 tester 에게 위임한다:
> "태스크 #A~#B 에서 구현된 기능에 대한 테스트를 작성하고 전체 테스트를 실행하라."

- RESULT: PASS → 4단계로
- RESULT: FAIL → 5단계로
- RESULT: NO_TESTS → tester 에게 테스트 환경 세팅을 먼저 위임하고 재시도

## 4. 리뷰 (Review)
reviewer 에게 위임한다:
> "태스크 #A~#B 의 변경 사항을 리뷰하라. docs/PLAN.md 기준으로 판정하라."

- PASS → 다음 마일스톤으로. 전부 끝났으면 6단계.
- FIX / REJECT → 5단계로

## 5. 보완 (Refine)
tester 의 FAILURES 또는 reviewer 의 BLOCKING 항목을 그대로 builder 에게 넘긴다:
```
수정 태스크: <원 태스크 #N>
문제:
  - <FAILURES / BLOCKING 항목 복사>
완료 조건: 위 항목 전부 해결 + 기존 테스트 통과
```
수정 후 3단계(테스트)부터 다시 돈다.

**보완 루프는 마일스톤당 최대 3회.** 3회 초과 시 STATUS.md 에 "STUCK" 으로 기록하고 사용자에게 다음을 보고한다:
- 무엇을 시도했고 왜 실패하는지
- 선택지 2~3개 (접근 변경 / 범위 축소 / 사용자 개입)

## 6. 완료 (Done)
1. `/verify` 스킬로 최종 점검.
2. STATUS.md 를 "DONE" 으로 갱신.
3. 사용자에게 보고: 만든 것, 실행 방법, 테스트 결과, 알려진 제한사항. 5줄 이내 + 파일 목록.

## 컨텍스트 절약 규칙
- 서브에이전트 답변은 정해진 보고 형식만 받는다. 형식을 어기면 다시 요청한다.
- 파일 내용을 직접 읽어야 할 때는 필요한 부분만 (Grep/부분 Read).
- 긴 진행 상황은 머릿속이 아니라 STATUS.md 에 쓴다.
