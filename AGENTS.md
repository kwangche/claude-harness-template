# Universal project harness

This is the common entry point for any coding agent. Read `docs/WORKFLOW.md` before
implementation and `docs/MODEL_POLICY.md` before choosing models. Runtime adapters
must use these rules rather than maintain a second workflow.

- The commander is the strongest tool-capable model **verified available in the
  user's current subscription**, selected by `.harness/cli.py route`. Check the
  runtime's model picker/catalog; record observation time and capability rationale.
  Never infer account access from a public model list, claim an unperformed switch,
  or silently use API billing. If another runtime wins, show its launch command or
  use `route --launch` in an interactive terminal. A running agent cannot assume
  changing a file changes its own model.
- The commander owns requirements, integration, workflow state and the final report.
  Use the host's native builder/tester/reviewer workers when available. Otherwise
  perform these roles sequentially and record review mode `sequential`; never claim
  an independent reviewer ran. A project can require independence in config.
- Before editing, start/resume a stable task ID. Configure argv commands in
  `.harness/config.json`. Run checks through the common CLI, including in a tester
  subagent, with the **same root and session ID**. Direct test commands are useful
  for diagnosis but cannot create a PASS receipt.
- Only the commander changes phase, records reviews, or updates PLAN. STATUS is
  generated by the CLI. Workers report `DONE`, `PARTIAL`, or `BLOCKED`, affected
  files, check receipts and remaining issues; PARTIAL is never a completed task.
- Choose `light` for a small, low-risk change and `full` for cross-cutting/security
  work. Both require current test evidence and review before DONE. Reuse matching
  evidence instead of repeating identical checks. Respect budgets; report STUCK or
  BLOCKED honestly when unresolved. Do not mark incomplete work DONE.
- Parallel writers require disjoint file ownership or separate worktrees and an
  explicit integration step. Default maximum: two workers. Run validation again
  after integration. Workers never race on shared STATUS or runtime state.
- Native sandbox/permissions are authoritative. The regex/token hook is only a
  supplemental guard. Read `docs/SECURITY.md`; never weaken permissions to fix a
  blocked check. Do not read secrets or modify verification records by hand.
- Before merging, inspect the exact PR diff and require green `harness-ci` on the
  expected PR head. Only merge when the user has authorized merging. Do not bypass
  branch protection or count missing/pending/skipped checks as a PASS.

Commands use Python 3.11+ and Git. Use `python .harness/cli.py --help`; if Windows
only has `py`, use `py -3.11` and update the Claude hook interpreter accordingly.
